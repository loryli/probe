## 16:55 修复「同一份 PDF 不会二次识别」（用户截图反馈）

- **根因**：`POST /materials/documents/{id}/extract` → `reextract_pdf()` → 直接调用 `upload_pdf()`，而 `upload_pdf` 先按 `sha256 + EXTRACTION_VERSION + mode` 查 `resume_extraction`，命中即返回，**根本不重跑**。用户点「重新提取」而策略没变（默认 auto）时瞬回旧文字，看起来像没有二次识别。已在 SQLite 佐证：`v6-102.pdf` 存在 `pdf-v3-layout-…:auto` 缓存行。
- **改法**：`upload_pdf(..., refresh: bool = False)`；`reextract_pdf` 传 `refresh=True` 跳过缓存读取，识别后由新的 `_store_extraction()` 覆盖同键缓存（失败结果不写缓存、也不拿旧值冒充）；上传路径仍复用缓存但返回 `DocumentRead.cache_hit=true`。
- **前端**：`MaterialsView` 上传命中缓存时提示「已直接复用已有识别结果，需要重跑请保存后点重新提取」；「重新提取」增加进行中提示与完成回执（耗时秒数、OCR 页码）。
- **验证（临时库 + 假识别器，未碰用户数据/未跑 pytest）**：`.cache/extract-check/run.py` 断言 5 步全过——首次上传调用 1 次；同字节上传 `cache_hit=True` 且不重复调用；重新提取调用第 2 次并返回新文字；再上传取到新缓存；缓存表只有 1 行且已覆盖。另复验 AST、`create_app()` OpenAPI 48 路径、`DocumentRead.cache_hit` 默认 false、两个 SFC 编译。
- **OCR 文字碎片（同一截图里的「表召回→字段 / I 01 + ← / gross_amount)」）**：对比 `pdf-v2` 与 `pdf-v3` 两版缓存，**该片段完全一致**——是扫描版 PDF 中流程图标签被 OCR 并进正文，不是排版版本问题；`text_layout` 只按坐标分行、不做版面结构识别，短箭头行还会被当作边界行不再合并。结论：重跑识别不会改善，需手工修正该行或后续重做版面分析（未擅自改排版规则，改动会影响全部简历）。

## 17:00 OCR 提取质量升级 pdf-v4（用户要求提高识别效果）

- **对照实验（真实扫描件 `v6-102.pdf` 第 1 页，直接跑真模型）**：
  - 基线 180dpi + det/rec small（v3 现状）：8.8s/页，流程图附近丢行 + 乱码「I 01 + ←」；
  - 300dpi + small：10.4s/页，恢复「匹配→Join 路径推理」但 `gross_amount)，Prompt…` 整行仍丢；
  - 300dpi + det/rec medium：103s/页，全对但太慢；
  - **300dpi + det-medium + rec-small：37.6s/页，全对** ← 选定；
  - 300dpi + det-small + rec-medium：69.6s/页，仍丢行（说明**检测模型**才是找到该行的关键）。
- **关键坑**：RapidOCR 默认 `Global.max_side_len=2000` 会把渲染图缩回去，只提 DPI 不放开该上限则收益被抵消（实验中 300dpi 组都配了 3000）。
- **改动（全部在 `materials/pdf.py`）**：`EXTRACTION_VERSION` → `pdf-v4-layout-rapidocr3.10-det-medium-300dpi`；`_engine()` 加 `Global.max_side_len=3000` + `Det.model_type=ModelType.MEDIUM`（`rapidocr.utils.typings` 导入失败时退回默认模型，兼容旧环境）；`_recognize_page` 渲染 `scale = min(300/72, 4200/max边)`。识别模型仍 small。
- **验证**：`extract_pdf` 全链路跑真实 PDF（auto 模式 2 页全 OCR）：72.8s，原错乱段落一字不差恢复，箭头乱码行消失；AST + `create_app()` OpenAPI 48 路径通过。medium det/rec 模型已被实验自动下载到 `data/ocr-models/`。
- **代价与边界**：单页 9s→38s，15 页以上整份扫描 force 模式可能超前端 600s 等待（服务端仍会完成并缓存，重试命中缓存）；**引擎参数按进程缓存，升级后必须重启服务**；其他机器首次使用会自动下载 medium 模型。仍未做版面结构识别（该文档实测已无碎片，但理论上流程图标签碎片可能出现）。
- 文档同步：README（行为说明/本轮完成项⑫/遗留问题/下一步）、`docs/frontend/BUSINESS_RULES.md`（提取质量配置属于提取版本，改动必须升级版本）。实验脚本 `.cache/ocr-experiment/` 已清理。

## 17:40 修复「第二个项目技术栈丢失」→ pdf-v5（用户截图）

- **现象**：OmniBot 项目只出现 `(qwen-plus)`，`【技术栈】` 整行没有；DB 里 `project.tech_stack` 为 `[]`。
- **取证**：三版缓存（v2/v3/v4）在该处都只有 `(qwen-plus)`；把该区域裁图给视觉看，原件实际是「【技术栈】Python·LangChain·LangGraph·LCEL·Milvus·DashScope·FastAPI·Redis·MySQL·通义千问 (qwen-plus)」。
- **根因（像素级矩阵实验）**：`Global.max_side_len=3000` 把 3508px 整页压缩到 3000（0.855x）后，这行灰色小字跌破检测下限。同页 `max_side_len=4200`（不压缩）→ 检出；关闭预处理 → 检出；350/650/1250px 局部带 → 漏检（比例极端）。`Global.min_height` 30/48/64 与 `Det.thresh` 降低均无效。

- **验证**：`extract_pdf` 全链路 2 页 95.1s，技术栈整行恢复（仍有一处单字误识「通义干问」），ChatBI 流程图段落仍正确。
