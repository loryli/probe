## 追问不落库的 bug 与「预生成 / 即时追问」原则

用户实战反馈两点：提问慢、追问效果差。只读查库拿到硬证据：决策轮 `elapsed_ms` 5658/6255/6700/6801/7440，输入 1360–1831 tokens、输出 123–152 tokens——**每次调用 6–7 秒，不存在异常慢**；慢在"每轮一次同步调用"。

- **真 bug**：`_apply()` 里 `next_turn`（追问 / 同目标续问）被赋值后**从未写库**，只有 `_next_turn()` 那条路会 `_create_turn`。于是决策记成 `action=follow_up`、`current_turn_id` 却是空，页面停在「当前没有待回答的问题」，用户点「继续生成下一问」才由 `_ask_next` 另生成一题——追问从未真正发生。这就是"追问效果不好"的直接原因。修复：`if next_turn is not None: await self._create_turn(...)`，并把原来的 `if next_turn is None` 改成 `else`。
- **策略收紧**：新增 `MIN_SUBSTANTIVE_ANSWER = 8`；回答短于 8 字（"不知道"/"草泥马"）时即使模型说 `follow_up_needed` 也不追问细节，落到基础问题或切题分支；`insufficient` + 有可追问措辞时，只要配额够就追问，不再依赖模型自报 `follow_up_needed`。追问措辞优先 `follow_up_question`，退化用同目标的 `next_question`。
- **提示词 v2**：`PROMPT_VERSION = "interview_prompt.v2"`，明确"不重复原题、不换说法再问"，答不上来或答非所问时改问该目标更基础的方面，而不是硬追。
- **等待可见**：前端 `startWait/stopWait` 把 `#answer-hint` 与 `#room-note` 改成"…已等待 N.Ns"的计时器（回答框隐藏时靠 `#room-note` 显示），替代静态文案。
- **原则落文档**：`docs/03` 新增「提问生成原则：基础问题预生成，追问即时生成」——不排整场题单（会退化成念脚本）、基础问题属骨架可预生成、追问必须即时、一次回答至多一次调用、追问是例外、等待可见；并记录实测耗时作为依据。README 行为条目、交接三段同步（下一步即实现 `interview_outline.v1` + `0008`）。
- 未验证：仍按约定未跑任何检查；新逻辑中"短回答不追问"依赖 8 字阈值，属经验值，需实战校准。


## 同一份计划每场问题都一样

用户反馈：同一份计划每次面试问的题完全相同。只读查库确认属实——3 场（`a8461126` / `0f14299c` / `3edc4b96`）都基于计划 `3a606d5c`，题库首题**逐字相同**。根因不是模型温度，而是整条出题链是计划状态的纯函数：目标永远从 `runtime.objectives` 顺序第一个开始，题库题永远 `question_ids[0]`（`cursor=0`），项目事实永远从 `facts[0]` 起按 `(asked-followups) % len(facts)` 取，提示词输入也完全一致；没有任何跨场状态参与。

- **新增 `interview/variety.py`**：`session_seed(session_id)` = `sha256(session_id)[:8]`，不落库、不新增迁移，同场次稳定可复现、不同场次不同；`shuffled`（按 `(seed, 元素标识)` 哈希排序）、`grouped_by_priority`（优先级分层不变、同层内打乱）、`prefer_unseen`（按历史出现次数稳定排序，没问过的排前面）。
- **改动 `service.py`**：`_bank_order` 替代 `_bank_question`（题库顺序 = 场次打乱 + 跨场未问优先，`_pick_bank` 按 `cursor` 取）；`_objective_order` + `_next_pending(session_id=)` 让目标顺序按场次变化；`_objective_facts(seed=)` / `_project_question(seed=)` 打乱事实顺序；`_next_turn` 改 async 并带 `plan_id/session_id`；新增 `_question_usage`（同计划其他场次每题计数，group by + join）与 `_avoid_questions`（近 6 条历史问题文本）。
- **事务边界**：缓存 `_usage` / `_avoid` / `_bank_orders` / `_objective_orders`，所有查询都在显式 `begin()` 块内完成，块外只用缓存——避免块外隐式开事务导致后续 `begin()` 报错。
- **提示词 v3**：`interview_prompt.v3`，`decision_payload` 增加 `asked_questions` / `avoid_recent_questions`（各 ≤6 条，不含标准答案），系统提示新增"不得与已问问题重复、不得换说法重问"；`question_messages` 增加 `avoid_recent_questions`。
- **温度单列**：`Settings.qwen_interview_temperature`（默认 0.8，env `INTERVIEW_QWEN_INTERVIEW_TEMPERATURE`），`QwenModel.generate` 与 `protocol.StructuredModel` 增加可选 `temperature`；只在面试判定/出题传，资料抽取不传，保证同一份资料抽取结果稳定。
- **原则**：考察目标、完成标准来自计划不可随机；从哪条证据、按什么顺序问由场次决定。不做整场随机抽样，避免高优先级目标被漏掉。
- **文档**：README 行为条目第 2/4 条改写、新增第 9 条与 env 示例；`docs/03` 新增「多场次多样性：考察目标固定，取题路径变化」。
- 未验证：按约定未跑迁移/测试/静态检查/浏览器；`seed` 派生顺序的观感、`prefer_unseen` 在题库耗尽后的轮转效果、0.8 温度对 JSON 稳定性的影响需实战确认。

## 基础问题骨架（interview_outline.v1 + 0008）

按上一轮确认的原则落地骨架：基础问题预生成、追问仍即时生成。

- **契约**：`schemas.py` 新增 `OutlineQuestion` / `OutlineObjective` / `OutlineDraft` / `SessionOutline`。`OutlineDraft.normalize` 容错模型输出的三种形态（questions 为字符串数组、字段写成 `question`/`id`、目标重复），每目标最多 `PROJECT_BASE_QUESTIONS`（2）题、题干截 300。`SessionOutline` 多一个 `source ∈ {model, rule, fallback}`，用于区分来源与降级；`questions(objective_id)` 供取题。
- **存储**：`interview_session.outline_json`（JSON，nullable），迁移 `0008_interview_outline`（`down_revision = "0007_interview_session"`，downgrade 用 `batch_alter_table` 删列）。旧场次为 NULL。
- **生成**：`_ensure_outline`（创建场次后、`_ask_next` 前）先读场次判断是否已有骨架，事务外调 `_build_outline`，再在第二个事务里带锁写回（`outline_json is None` 才写）。`_build_outline`：规则模式或无项目目标 → `_rule_outline`（用 `rules.project_question` + 场次 seed 打乱后的事实，取前 2 条）；模型模式未配置 → `fallback`；模型调用 `ModelError` → 记 warning 后 `fallback`，**不阻断创建**；返回后按 runtime 目标 ID 过滤，全空也记 `fallback`。
- **提示词**：`OUTLINE_PROMPT_VERSION = "interview_outline_prompt.v1"`、`OUTLINE_SCHEMA_VERSION = "interview_outline.v1"`；`outline_payload` 只发 project 目标、每目标最多 4 条事实 × 260 字、`completion_rule` 截 200，避免批量输入过大；`outline_messages` 对应。
- **取用**：`_outline_question(outline, objective, state)` 用 `state.asked - state.followups` 作索引（即已问过的基础问题数）。`_ask_next` 在 rule/模型分支前先试骨架，命中即 `_open_turn` 零调用；`_next_turn` 改为 `outline` 必传，骨架 > 模型 `fallback_text` > 模板；`_apply` 的同目标第二问也改为骨架优先（否则模型总填 `next_question`，骨架第 2 题永远用不上），追问分支不受影响。
- **一致性**：`_base_remaining` 对 project 目标是 `2 - (asked - followups)`，与骨架 2 题一一对应；骨架缺失时逐级回退到规则模板与即时生成，行为与改造前一致。
- **前端**：开始按钮在创建期间显示「正在生成题单…」，`#connection` 同步；`interview.html` 说明文案改为「开始时会一次生成各目标的基础问题（首次需等待十几秒）；之后切题直接取用，追问才调用模型」。
- **文档/测试**：README 行为第 2 条改写、新增第 10 条（骨架只覆盖基础问题、追问仍即时）、迁移 head 改 `0008_interview_outline`、交接三段重写；`docs/03` 在「基础问题预生成」下补「骨架已落地」；`tests/test_local_database.py` 版本断言改 `0008_interview_outline`。
- 未验证：按约定未跑迁移/测试/浏览器/模型调用，只做了 `ast.parse` 语法解析。以下均待实测：批量生成的耗时与失败率、`outline_json` 实际写入与取用、骨架在题库目标与旧场次上的回退、`_apply` 骨架优先后的提问观感。
