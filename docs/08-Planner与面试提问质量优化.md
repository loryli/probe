# Planner 与面试提问质量优化

- 审查日期：2026-11-24
- 审查范围：当前工作区的 Planner、Interview Agent、计划页面及相关设计文档
- 文档状态：**设计审查与改进建议，尚未批准实施**
- 本次只做阅读和文档整理，没有修改业务代码，也没有运行测试、静态检查或浏览器验证

## 1. 结论

Planner 的整体方向可以保留：冻结资料版本，由服务端管理引用、时间预算和追问上限，模型只负责语义目标与局部提问。不需要推翻重做，也不需要通过更换模型或增加复杂编排来解决问题。

当前提问质量的主要瓶颈不在「Planner 输出目标」这一单独环节，而在整条链路：

1. 前端候选范围随机，岗位层级和难度信息不足。
2. Planner 看到的是裁剪后的资料，输出目标又过于抽象。
3. 项目面试预写两个基础问题，动态提问实际退化为半固定题单。
4. 决策只保留最近 3 轮，目标覆盖依赖模型自评，缺少跨轮证据约束。

因此，优化重点应是：**让目标可执行、让资料足够具体、让提问真正跟随回答，并让目标覆盖有证据可查。**

## 2. 当前真实链路

### 2.1 计划生成

1. 计划页默认随机抽取最多 40 道题，用户可手动调整：[`frontend/src/views/PlannerView.vue:85`](../frontend/src/views/PlannerView.vue#L85)。
2. 规划配置主要包含练习方式、简历版本、项目/题目范围、训练方向、时长、追问上限、题源比例和已确认记忆；没有目标岗位、候选人层级或难度：[`frontend/src/views/PlannerView.vue:313`](../frontend/src/views/PlannerView.vue#L313)。
3. Planner 输入项目摘要、事实和题干的短前缀，以及已确认记忆：[`src/interview_assistant/planner/prompt.py:62`](../src/interview_assistant/planner/prompt.py#L62)。
4. Planner 输出主题、优先级、可观察证据、引用、完成条件和追问建议；预算与配额由服务端计算。
5. 引用会做 ID 存在性和来源校验，但不会验证主题与引用内容是否语义相关：[`src/interview_assistant/planner/service.py:540`](../src/interview_assistant/planner/service.py#L540)。
6. `candidate_scope` 当前保存所选来源的全部事实和题目，不是经过筛选的相关子集：[`src/interview_assistant/planner/service.py:772`](../src/interview_assistant/planner/service.py#L772)。

### 2.2 面试执行

1. 简历面试先进行自我介绍和项目介绍。
2. 项目目标按需生成 outline；模型模式通常为每个项目目标预写两个基础问题：[`src/interview_assistant/interview/questioning.py:156`](../src/interview_assistant/interview/questioning.py#L156)。
3. 基础问题按 outline 顺序使用，当前实现不是「整场开始前一次生成」：[`src/interview_assistant/interview/questioning.py:232`](../src/interview_assistant/interview/questioning.py#L232)。
4. 回答后只取最近 3 轮进入决策上下文：[`src/interview_assistant/interview/service.py:86`](../src/interview_assistant/interview/service.py#L86)、[`src/interview_assistant/interview/service.py:818`](../src/interview_assistant/interview/service.py#L818)。
5. 模型在内部流式接收完整结果，校验并落库后才展示实际下一问；没有把未校验的 `say` 增量转发给页面：[`src/interview_assistant/interview/service.py:905`](../src/interview_assistant/interview/service.py#L905)。
6. 当同目标还有基础题时，服务端优先使用 outline，决策生成的 `say` 不会替换它：[`src/interview_assistant/interview/service.py:1061`](../src/interview_assistant/interview/service.py#L1061)。
7. 模型自评 `covered` 后，服务端直接推进，没有独立的必填证据检查：[`src/interview_assistant/interview/service.py:1033`](../src/interview_assistant/interview/service.py#L1033)。
8. 纯题库最终从冻结原题取题，不接受模型自拟追问；但场次选择模型模式时，推进原题仍依赖一次实时决策调用。

## 3. 问题清单与解决方案

优先级定义：

- **P0**：可靠性或流程正确性问题，应优先处理。
- **P1**：直接影响提问质量，建议作为质量优化主线。
- **P2**：提升可审查性和可控性，可在主线稳定后处理。

| 优先级 | 问题 | 当前影响 | 建议方案 |
|---|---|---|---|
| P1 | 目标缺少考察点和切换条件 | 目标只能表达「考什么」，不能表达「怎么考、何时继续」 | 增加 `probe_points` 与 `switch_condition`，把完成规则改为最低证据要求 |
| P1 | 项目 outline 预写两个基础题 | 第二问无法根据第一问回答调整，动态提问退化 | 只预生成首问，或取消 outline；后续问题依据回答缺口即时生成 |
| P1 | 决策上下文缺少目标级历史证据 | 容易重复提问、遗忘早期证据或过早切题 | 维护有界的目标证据摘要，并随每次决策回流 |
| P1 | Planner/面试资料被固定前缀裁剪 | 关键条件、取舍和结果可能没有进入模型 | 先相关性筛选，再对入选资料按 token 预算完整或分段发送 |
| P1 | 默认随机抽题，缺少岗位与层级 | 计划范围不可预测，难以区分基础题与深入题 | 默认按方向/岗位/层级/难度筛选，随机只作为换题操作 |
| P1 | 覆盖判定依赖模型自评 | `covered` 可能没有足够证据 | 用必填考察点作为覆盖门槛，证据不足时继续 probing 或明确留空 |
| P0 | 纯题库模型决策失败会卡住原题 | 不需要生成的问题也会因模型配置或调用失败中断 | 纯题库直接推进原题游标，跳过实时出题决策；独立分析与复盘保留 |
| P2 | 引用只验 ID，不验语义相关性 | 合法 ID 也可能支撑无关目标 | 确认页展示逐目标引用，允许禁用目标或重新配置 |
| P2 | `candidate_scope` 与题目队列语义不清 | 候选题可能被全部当作必问题 | 明确候选池与待问队列；纯题库仍问完所选原题 |
| P2 | 计划只能整体确认 | 用户难以纠正单个目标，只能整份重生成 | 支持禁用单目标、调整优先级，并由程序重算预算 |
| P2 | 最近 30 条记忆默认全选 | 无关旧证据可能影响当前优先级 | 默认不选或只选方向相关记忆，保留人工排除 |

### 3.1 目标需要「考察路线」，而不是更多抽象标签

当前 `PlanObjective` 只有主题、可观察证据、完成规则、引用和预算：[`src/interview_assistant/planner/schemas.py:250`](../src/interview_assistant/planner/schemas.py#L250)。

Planner 提示词又禁止主题包含具体技术路径、场景或指标，并限制完成条件不写具体步骤：[`src/interview_assistant/planner/prompt.py:29`](../src/interview_assistant/planner/prompt.py#L29)。这有助于避免 Planner 越权生成固定题单，但也使输出过于笼统。

例如：

```text
topic: RAG 可靠性
observable_evidence: 能说明取舍依据
completion_rule: 能解释关键设计
```

这些字段不足以指导下一问。建议增加少量结构化中间层：

- `probe_points[]`：2–4 个考察角度。
- 每个考察点包含 `aspect`、`expected_evidence`、`depth`。
- `switch_condition`：满足什么条件后换角度或切目标。
- `completion_rule`：明确必须得到的最低证据，而不是「能够说明」。

示例仅用于表达结构，不是已确认提示词：

```json
{
  "topic": "RAG 可靠性",
  "probe_points": [
    {
      "aspect": "检索问题定位",
      "expected_evidence": "说明如何区分召回不足与排序问题，并有验证依据",
      "depth": "深入"
    },
    {
      "aspect": "质量验证",
      "expected_evidence": "说明评估集、指标或人工复核方式",
      "depth": "深入"
    },
    {
      "aspect": "失败降级",
      "expected_evidence": "说明检索不可靠时如何控制回答风险",
      "depth": "基础"
    }
  ],
  "switch_condition": "当前考察点有具体证据且无关键缺口时进入下一点；连续缺少可追问内容时换基础角度",
  "completion_rule": "至少对两个必填考察点给出做法和验证依据"
}
```

约束仍需保留：

- 预算、次数和状态转换由服务端管理。
- `probe_points` 不是完整问题清单。
- 不要求模型编造资料中没有的技术细节。
- 标准答案不进入面试官出题上下文，避免问题泄露答案。
- 新字段只用于新计划；旧已确认计划保持冻结，不静默补写或升级。

### 3.2 项目 outline 与动态提问的边界需要调整

当前 outline 提示词要求每个项目目标写两个问题，随后按顺序使用。这解决了切题时等待模型的问题，但也带来两个质量问题：

- 第二问在候选人回答前已经决定，不能针对第一问缺口调整。
- 决策模型认为需要换角度时，服务端仍可能优先取 outline。

建议优先采用：

1. 项目目标只预生成首问，首问用于降低开场等待。
2. 回答后根据目标考察点、当前回答和历史证据决定下一问。
3. 服务端只校验目标范围、重复、来源和追问额度，不无条件用骨架覆盖合法动态措辞。
4. 模型失败时保留规则降级，不把动态提问重新变成整场固定题单。

如果暂不调整 outline 数量，至少应允许满足以下条件的 `say` 替换基础题：仍属当前目标、有明确回答缺口、不与已问题目重复、追问额度允许。被拒绝的追问不得改名为普通基础题保存。

### 3.3 用目标证据摘要替代「只有最近 3 轮」

当前决策只发送最近 3 轮，且没有把较早 observation 汇总后回流。建议在每个目标的进度中维护有界证据摘要：

- 已问过哪些角度；
- 已得到哪些具体证据，引用回答轮次；
- 哪些考察点仍缺失；
- 哪些主张矛盾或待核验；
- 当前已完成的基础题与追问数。

摘要应有长度和条目上限，不把整场 transcript 重新塞入每轮请求。模型可以建议更新摘要，但服务端只接受可回溯到真实轮次的内容，并保留暂停、恢复和重试时的状态一致性。

目标覆盖建议改为：

- 必填考察点均有足够证据时，才允许标记 `covered`。
- 有缺口但仍有价值时，选择缺口对应的角度。
- 回答过短、答非所问或没有可追问内容时，换基础角度或切目标，不反复逼问同一件事。
- 材料不足或额度耗尽时明确说明未覆盖，不伪装成已达标。

### 3.4 先筛选资料，再扩展上下文

当前 Planner 输入为固定前缀：摘要 200 字、事实 120 字、题干 80 字；面试决策的事实和近期对话也有固定长度上限。快照中的完整答案和笔记不一定会进入模型。

建议采用两段式上下文：

1. **筛选阶段**：用短资料、方向、岗位和元数据确定相关目标与事实。
2. **执行阶段**：只对当前目标发送更完整的相关资料，按 token 预算裁剪。

具体边界：

- 用户笔记可以作为提问偏好，但不能覆盖题干、答案或项目事实。
- 项目事实保留来源引用；未知内容不补写。
- 题库标准答案只用于独立回答分析或复盘，不发送给实时出题模型。
- 长资料优先按语义段落选择，不只保留开头。
- 跨轮历史以证据摘要替代全文，控制延迟和费用。

### 3.5 选材从「随机范围」改为「相关范围」

当前默认随机抽题，且页面没有岗位、年限、难度或重点题型。建议：

- 规划输入增加目标岗位类型和候选人层级，允许留空。
- 已有题库元数据足够时，按方向、分类、难度和知识点筛选默认候选。
- 没有元数据时先由用户选择范围，不假装系统已经理解题目难度。
- 「随机重选」只用于在已筛选范围内换题。
- 默认记忆改为不选或仅选与本次方向相关项；最终是否采用由用户确认。

### 3.6 明确候选池、题目队列与计划审查

`candidate_scope` 当前只是全部所选资料，而 Interview 实际按目标的 `question_ids` 取题。建议明确两种语义：

- **候选池**：模型认为与目标相关、可以从中选择的资料。
- **待问队列**：本场真正要按顺序消耗的题目。

纯题库继续遵守产品边界：只问用户所选原题，不生成额外追问。简历混合面试则可以从同一目标的候选题中选择更合适的一题，避免把 Planner 关联的所有题目都问完。

计划确认页建议展示：

- 每个目标引用的事实或题目原文；
- 目标之间的重复引用；
- 未覆盖资料与限制说明；
- 禁用单个目标、调整优先级的操作；
- 调整后由程序重算时间与追问预算，不默认重新调用 Planner。

## 4. 纯题库实时决策问题

这是独立于 Planner 质量的执行问题。

当前纯题库计划使用规则规划，但创建场次时仍可选择模型反馈模式。该模式下，回答后会先调用实时决策模型；模型未配置、超时或输出非法时，服务端写入错误并返回，下一道原题因此卡住：[`src/interview_assistant/interview/service.py:895`](../src/interview_assistant/interview/service.py#L895)。

建议：

- 识别 `runtime.resume_id is None` 的纯题库场次。
- 回答保存后直接读取并推进冻结原题游标，不等待出题决策。
- 保留独立的逐轮回答分析和整场复盘能力。
- 模型分析失败只影响分析任务，不影响下一道原题。
- 不把纯题库的模型反馈称为动态提问，因为产品边界禁止 AI 自拟追问。

## 5. 模型参数与提示词调整

当前配置中，Interview 使用 `qwen_interview_temperature=0.8`，Planner 不单独传 temperature，thinking 默认关闭：[`src/interview_assistant/config.py:34`](../src/interview_assistant/config.py#L34)。

这些参数可以作为后续 A/B 因素，但没有真实失败样本前，不应认定它们是问题主因。建议先固定一批代表性计划和回答，再比较：

- 问题与目标的相关性；
- 是否问到具体做法、依据和结果；
- 是否重复或过早切题；
- 是否编造项目事实；
- 首问与决策延迟；
- 单场模型调用次数和费用。

一次只改一个因素，避免同时更换模型、提示词、上下文和温度后无法判断收益来源。

## 6. 建议实施顺序

以下顺序是设计建议，不是已批准的开发计划。

### 第一批：低成本修正

1. 纯题库跳过实时出题决策，直接推进原题。
2. 修正文档中 outline 与流式决策的过期描述。
3. 计划页展示逐目标引用，先解决「看不见依据」的问题。

### 第二批：提问质量主线

1. 为目标增加考察点和切换条件。
2. 项目 outline 改为只生成首问，后续动态提问。
3. 增加目标级跨轮证据摘要，并用必填考察点约束覆盖。
4. 对当前目标发送更完整的相关资料。

### 第三批：选材与计划可控性

1. 增加岗位类型、层级和难度输入。
2. 用相关性筛选替代默认随机选题。
3. 明确候选池与题目队列。
4. 支持禁用单目标和调整优先级。
5. 调整记忆默认选择策略。

### 第四批：效果评估

1. 用同一批资料比较优化前后的计划与提问。
2. 检查相关性、具体性、重复率、证据约束和延迟。
3. 根据真实样本决定是否调整模型参数或提示词。

## 7. 验收标准

优化完成后，建议由用户通过真实页面和面试记录验收以下行为：

### 计划质量

- [ ] 同一配置下，默认选题范围可解释，不再由纯随机决定。
- [ ] 岗位、层级或难度变化能反映在目标深度和选题中；留空时仍可正常规划。
- [ ] 每个目标至少有两个具体考察点，并明确最低完成证据。
- [ ] 目标引用能在确认页展开查看，用户可禁用明显不合适的目标。
- [ ] 候选资料与真正待问题目有清晰语义，不把全部候选题默认问完。

### 实时提问

- [ ] 项目首问之后的问题会随候选人回答改变，而不是固定念第二题。
- [ ] 同一目标内不会重复询问已经讲清的内容。
- [ ] 缺口明确时追问具体做法、依据或结果，不停留在泛泛介绍。
- [ ] 较早轮次的有效证据能影响后续决策，不会被最近 3 轮窗口遗忘。
- [ ] 必填证据不足时不会仅凭模型一句 `covered` 提前切题。
- [ ] 回答过短或答非所问时换基础角度，不进行无效逼问。
- [ ] 动态措辞仍受目标范围、来源、去重和追问额度约束。

### 可靠性

- [ ] 纯题库在模型未配置或决策调用失败时仍能继续下一道原题。
- [ ] 独立回答分析和复盘失败不会阻塞题库原题。
- [ ] 已确认旧计划继续按冻结快照运行，不被新字段静默改写。
- [ ] 模型请求不自动重试收费调用，重复请求仍读取原任务。
- [ ] 用户题干、答案、笔记、简历和事实原文不被 AI 元数据或生成结果覆盖。

## 8. 与旧设计稿的关系

本文以当前源码为准，校正以下历史描述：

- 项目目标当前确实会预写最多两个基础问题，但属于按目标增量生成，不是提前排完整场题单。
- 实时决策当前在内部流式接收，完整校验并保存后才推送下一问；不会把未校验的 `say` 增量展示给用户。
- 旧设计稿中「基础题只作兜底，模型 `say` 原样落库」不是当前实际行为；同目标基础题仍优先使用 outline。

相关现状参见[实时面试状态机与数据流](./03-实时面试与分析数据流.md#提问生成原则当前实现与质量审查)和[Prompt、结构化输出与 API 草案](./04-AI契约与API草案.md#23-interview-planner)。后续若决定调整 schema、outline 或页面交互，应先更新对应契约与版本策略，再修改代码。
